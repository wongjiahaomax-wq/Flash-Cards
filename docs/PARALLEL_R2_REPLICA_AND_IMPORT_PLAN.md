# Parallel R2 transfers for the local replica and reviewed import

Status: planning handoff; implementation belongs in **this same Draft PR**.

## Goal

Reduce waiting caused by sequential independent R2 object operations in two existing workflows. No performance benchmarks are requested; a bounded-concurrency implementation with correct behavior is sufficient.

## Tranche A — local production-asset replica

Owner: `scripts/refresh-local-replica.mjs` and directly related tests/helpers.

Current behavior: `refreshR2()` synchronously downloads each production R2 object with Wrangler, then synchronously puts it into local R2, before starting the next asset.

- Use a simple bounded pool with **four concurrent remote GETs**. Each asset's local PUT follows its successful remote GET; local PUTs are **serialized from the outset** to avoid shared local Wrangler/R2 contention, while independent remote downloads may continue. Keep the repository-pinned Wrangler and existing argument builders.
- Use async child-process execution so up to four remote Wrangler downloads genuinely overlap; keep the local write lane serial without blocking unrelated remote GETs. Preserve cross-platform Node execution, safe per-key staging filenames, per-asset cleanup, and useful bounded failure reporting. Await all started downloads/writes before removing the shared staging directory.
- Preserve the current content/Asset allowlist, production D1 SELECT and R2 GET **only**, local D1/R2 writes only, original object keys/MIME types, existing local reset semantics and commands, and the existing zero-success failure behavior.
- Keep a bounded concurrency limit even for large asset libraries. Do not add a dependency, new credential, remote write path, or storage redesign. Leave unrelated sequential D1 table snapshot reading unchanged.

## Tranche B — reviewed-import startup staging

Owners: `src/lib/server/storage/import-packages.js` (bounded media PUTs and compensation), `src/lib/server/import/resumable-content-package-runtime.js` (initial job creation/ownership, fail-closed process claim and staging transition), `src/lib/server/import/resumable-content-package.js` (cancellation/cleanup guards), and `src/routes/admin/import/+page.svelte` (Retry/Resume visibility). Touch the directly related client controller/tests only as necessary. These are one coherent Tranche B change, not separate PRs.

Current behavior: `stageImportPackage()` stores the ZIP, then stores the execution-plan sidecar and each create-Asset media object sequentially. The Admin Start action waits for this staging to finish before returning a job and starting the browser's resumable processing loop.

- Preserve package preflight, exact-preview SHA confirmation, capacity/accounting checks, immutable conditional object creation, canonical private keys, and the original ZIP/plan snapshot contracts.
- Keep ZIP and plan staging in their existing order; use a bounded **four-upload** pool for independent derived create-Asset media objects only. Do not parallelize jobs, D1 import/validation phases, or browser process requests.
- On a failed media upload, stop scheduling new uploads and await settlement of **all started writes before compensation**. Track every successfully created staging key (including ZIP/plan), remove only keys owned by this job, and never race cleanup against an in-flight PUT. A failed cleanup may leave private staging debris, but must never make the job processable. Keep the existing staging-cleanup/cancel pathway available; do not delete another job's objects or imported teaching media.
- **Explicit staging readiness gate (blocker):** The current job is inserted with `status='validating'` before staging, and ordinary `status='failed'` jobs can be resumed. Do not rely on ZIP/plan existence, successful response delivery, or best-effort cleanup as proof of complete staging. Insert a new job in the existing `phase='staging'` (existing schema permits text phases), and move to the first validation phase **only after every required R2 PUT succeeds**. Its `status` can retain an existing allowed value; distinguish staging readiness by the phase. The **initial processing claim AND subsequent processing logic** must reject `staging`/`staging_failed` and any other incomplete-staging state, even on a direct request, without validation or domain writes. Disallow ordinary Retry/Resume for staging failures in the server and Admin UI; a new import may be started from the exact reviewed ZIP. Preserve Retry/Resume for jobs that completed staging and later failed during validation/import.
- **Atomic initial ownership and fenced transitions (blocker):** Prefer inserting the job with its initial staging lease/ownership token **in the same D1 INSERT** that creates `phase='staging'`, eliminating a cancellable gap between creation and ownership. If a separate claim is required, it must conditionally acquire ownership before the first R2 PUT; a rejected claim starts no uploads. Stage only while holding that token. On success, conditionally update the **same token + expected staging phase/status** to the first validation phase and release ownership **after all required R2 PUTs succeed**. On failure, settle all started writes, compensate, then conditionally update the same token + expected staging phase/status to non-resumable `staging_failed` and release ownership. A failed conditional update must not overwrite `cancelled`, release another owner's token, or begin further uploads. Cancellation must conditionally reject an owned staging job and must not delete its objects while any PUT remains in flight, **even after lease expiry**; provide a clear busy/deferred result. After staging has fully settled and ownership is released, cancellation/cleanup may proceed for `staging_failed`. If a Worker is interrupted with staging ownership unresolved, keep it unprocessable and retain private staging; do **not** treat lease expiry alone as proof that a previous upload stopped or that deletion is safe. A fresh import under a new job ID remains available; do not add a background cleaner, schema migration or speculative recovery framework.
- Keep `import_assets` processing, leases/fencing, deterministic teaching-image immutability, D1 checkpoints/budgets and idempotency unchanged. No schema, new endpoint, Queue, Durable Object, background worker, ZIP re-upload redesign, or generalized concurrency framework.

## Executable acceptance

1. Focused local-replica tests with stubbed asynchronous Wrangler operations prove: at most four concurrent remote GETs, overlapping remote GETs while local PUTs remain serialized, each PUT follows its matching successful GET, independent failures are reported, staging files are cleaned only after workers settle, and no production mutation argument is introduced. No live production reads/writes solely for testing.
2. Focused import-staging tests with a controllable R2 fake prove: media PUTs overlap up to four; no more than four are in flight; ZIP/plan and SHA/key/content contracts remain intact; a failed PUT settles other in-flight PUTs before cleanup, including when cleanup itself fails; and success is unchanged.
3. **Actual runtime/process-action regression:** Exercise the initial job-creation/ownership boundary: cancel immediately after the D1 job is created but before the first PUT (or before a separate staging claim is obtained); prove staging has initial ownership atomically, or a lost claim starts no uploads and cannot overwrite cancellation. Hold a staging PUT pending; prove both the initial process claim and subsequent process path reject incomplete staging, and a concurrent cancel cannot mark the job cancelled or delete objects. Include expired staging ownership: expiry alone must not permit deletion while an earlier PUT remains in flight. After writes settle, prove success/failure updates require the original token + expected staging phase/status; a stale completion/failure handler cannot overwrite cancellation or another owner. Prove full staging advances to validation, incomplete/failed staging cannot resume even after partial cleanup failure, and post-staging validation/import failures retain normal resumability. Cover the Admin Retry/Resume affordance for staging failures with the smallest appropriate UI/controller test. Reuse existing runtime-safety tests for unrelated lease/checkpoint behavior rather than introducing new architecture.
4. Run focused tests during iteration, then repository-required `agent:checks` handoff validation and specialized checks. Report what ran and exact-head CI. No speed benchmarks or timing thresholds.
