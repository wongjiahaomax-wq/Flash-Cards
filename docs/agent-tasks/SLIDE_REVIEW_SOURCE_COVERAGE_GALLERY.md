# Source Coverage — complete-slide gallery and large viewer

Status: **implementation plan only**. Implement within this same Draft PR; no reviewer code has been changed by the planning commit.

## Product outcome

In the **existing offline Slide Import Reviewer**, the **Source coverage** control opens its existing coverage workspace. Keep its current list/table as the default view, and add a `List | Gallery` switch **inside Source Coverage**. The gallery must expose **every original slide/page in the loaded review bundle**, in `sourceFiles` order and ascending page number **within each source**, regardless of the order of `sourceCoverage[]`; include non-Case, title, reference and answer slides. This is for inspecting the entire deck alongside the existing Case reviewer; it is not a new authoring or editing surface.

## User experience and acceptance

1. **Complete, legible gallery.** Desktop gallery uses **two generously sized thumbnails per row**, filling available Source Coverage width; narrow/mobile uses one per row. Preserve each original image's aspect ratio (no cropping). Display original slide/page number and existing classification / linked Case context (where present). For multiple source files, clearly separate or label decks with filenames and restart numbering per source. Derive gallery order from `reviewMap.sourceFiles[]` and ascending page number per source, **not** from `sourceCoverage[]` insertion order. Missing/unavailable preview paths get a clear placeholder while the coverage row remains present.
2. **Large slide viewer.** Clicking any available slide image opens a viewport-filling viewer that uses the **existing source-preview image**, not a low-resolution cropped thumbnail. Fit the whole slide initially within the available viewport, preserving aspect ratio. Provide accessible Close, Previous, Next, and zoom controls with fit-to-screen and **100% native-pixel** inspection; allow zoom above 100% and pan when zoomed. The image should occupy most of the display rather than an existing small Case-source panel. Never promise resolution beyond what the review ZIP actually supplies.
3. **Complete deck navigation.** Previous/Next traverse consecutive source pages in the same `sourceFiles`-then-ascending-page order as the gallery, **including non-Case slides**, even if `sourceCoverage[]` is shuffled; do not filter by Case status or coverage classification. Show source filename and original page number so multiple-deck bundles are unambiguous. Closing the large viewer returns to the gallery at the same slide/scroll position. Switching back to List preserves the existing coverage behavior.
4. **No lost work.** Opening/closing Source Coverage, switching List/Gallery, opening the slide viewer and navigating slides **must not discard unsaved Case edits or change current Case/review progress or status on their own**. **An actual edit to approved Case/Question/Asset content must still trigger the reviewer's existing approval-invalidation behavior** (including an edit committed when entering Source Coverage); entering or navigating the gallery alone must not invalidate approval. Existing editable fields commit some changes only on `change`; entering Source Coverage must commit a currently focused, modified Case field through the existing edit/persistence path **before replacing its DOM** (including when the user clicks Source Coverage immediately after typing, without manually blurring first). Do not silently discard other uncommitted reviewer input: in particular, an **unfinished crop session** or **unresolved-question Prompt/answer input** must be preserved on return, or entry to Source Coverage must be blocked until the user explicitly finishes/cancels the operation. Do not silently cancel a crop or drop unsubmitted unresolved-question answers. Keep the existing per-Case source viewer and crop workflows intact; do not reset or reload the review bundle.
5. **Case-action isolation.** While Source Coverage **or its viewer** is active, existing Case toolbar controls (Previous/Next, status actions, and Case filter) and Case keyboard shortcuts (navigation, reveal, approve, needs-review, reject) must neither invoke Case actions nor change underlying Case selection, filter, status, review state, or reveal state. Disable or hide the inactive Case controls and guard their handlers so stale or programmatic callbacks cannot mutate Case state. Slide-viewer navigation/close keys act only on the viewer. Restore Case controls and shortcuts when returning to Case review. Keep the separate backup/finalization behavior unchanged.
6. **Transition-safe rendering and persistence.** The current Case render loads images asynchronously before replacing the workspace DOM, and edit/persistence callbacks may trigger a subsequent Case rerender. Once Source Coverage is entered, neither a late Case render **nor a delayed edit/persistence completion** may replace the active coverage List/Gallery or viewer, switch the chosen coverage mode, or reset its selected slide/scroll position. Check the active view at the actual DOM-commit point, including after awaits; preserve gallery/viewer state through any legitimate coverage refresh. Keep this within the existing rendering/edit lifecycle—no new state-management architecture.
7. **Viewer focus.** On open, move keyboard focus into the viewer, make its controls operable without triggering Case shortcuts, and on close restore focus to the thumbnail/control that opened it (or its nearest available gallery fallback). Escape closes the viewer without closing Source Coverage or changing the underlying Case. Preserve gallery scroll position and selected slide.
8. **Offline and responsive.** Use `reviewMap.sourceFiles`, `reviewMap.sourceCoverage[].previewPath`, and source previews **already inside the opened ZIP**. Do not require internet, a server, API, new extraction output, or a schema change. Preserve existing lazy archive/image loading and bounded caching: entering the gallery must not eagerly decompress/decode every full-resolution slide for large decks, or create/retain a full-deck set of image object URLs. Load only the visible (or a small adjacent) gallery subset and the selected viewer image using existing file-store/preview URL lifecycle where possible. **Cache eviction must not revoke a URL still used by a displayed gallery thumbnail or the open viewer**; release it only when no longer displayed, then keep the cache bounded as the user scrolls/navigates. Do not invent a second cache architecture.
